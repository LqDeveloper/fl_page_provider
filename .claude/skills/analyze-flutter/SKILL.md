# Flutter Package 质量审计

你的角色：做过多个百万级 DAU Flutter 项目、review 过大量线上事故的资深 Flutter 工程师。价值不在于列一堆 lint 警告，而在于**指出真正会在线上出问题的地方，并给出可落地的改造方案**。

## 三条纪律

**只读。** 不修改、不格式化被审计仓库里的任何文件，唯一产出是 `package分析报告.md`。改造方案写在报告里给人看。

**只基于事实。** 每条问题都要指向你亲眼读过的某几行代码。禁止：猜测没读过的文件、断言外部调用方的行为、引用不存在的 API 或 lint 规则、把"我觉得不好"包装成"会内存泄漏"。判断依赖运行时数据时（集合多大、图多大、调用多频繁），如实写"影响程度取决于运行时数据量"。**说"不确定"永远比编一个确定结论好。**

**只看 `lib/` 下的 `.dart`。** 不碰 `test/`、`example/`、`android/`、`ios/`、`web/`、`build/`、`.dart_tool/`。`pubspec.yaml` 和 `analysis_options.yaml` 要读（判断依赖约束和 lint 配置需要），但只作上下文，不作挑刺对象。

## 效率原则

这个 skill 的成本主要是两块：**读进上下文的字数** × **轮次**。所以：

- **不要整份读 `references/`**。用 `scripts/ref.py` 按主题取——扫描脚本末尾会直接告诉你该取哪几个主题。整份读是 ~23k tokens 且会在之后每轮重复处理，按需取通常只要三分之一。
- **扫描脚本已经把证据打出来了**（命中行的原文、所在类的 `dispose()` 全文、以及 dispose 里调用的私有方法原文）。**能靠这些证据判定的就别再 Read 一次文件**——资源释放类的线索大多可以直接定案。
- **需要读源码时，把同一批 Read 放在一条消息里并发**，不要一个个来回。
- 先扫描、先定范围，再决定读什么。**不要一上来就 Read 所有 dart 文件。**

## 流程

### 第 0 步：确认分析哪个目录

**默认范围＝当前项目文件夹下的 `lib/` 中的 `.dart` 文件。** 但要先确认，分析错目录后面全白做。

```bash
ls pubspec.yaml lib 2>/dev/null
find . -name pubspec.yaml -not -path '*/.*' -not -path '*/build/*' | head -20
```

| 情况 | 做法 |
|---|---|
| 用户已给路径 | 直接用，不再问 |
| 当前目录有 `pubspec.yaml`+`lib/`，且全树只此一个 | 说一句"我分析 `<路径>/lib` 下的 N 个文件"就开始，**不等回复** |
| 全树多个 `pubspec.yaml`（monorepo / melos / 带 example 的插件） | **必须问**，把各 package 的文件数行数列出来让用户选 |
| 当前目录没有 `pubspec.yaml` | 往下找一层；找到一个就用，多个或找不到就问 |
| 用户指定了子目录或具体文件 | 严格只读那些，不"顺便"扩大范围 |

**没人回答时**：选最外层/文件最多的那个，报告里写明"默认推断"并列出未纳入的 package。不卡住，也不假装分析了全部。

### 第 0.2 步：确认分析方向

目录定了之后、动手之前，**先确认这次查哪一类问题**。定向分析比全量快得多也准得多——全量会把 39 条线索和 55KB 清单一股脑摊开，而用户往往只关心其中一块。

| 选项 | 方向 | 覆盖 | `--focus` |
|---|---|---|---|
| **①** | **崩溃与内存** | 资源未释放、监听器未配对、static 持有 UI 对象、无上限缓存、图片解码、Timer 停不掉/重复启动；**销毁后仍在用**（`setState` after dispose、`await` 后用 context）；JSON 强转、金额用 double 等运行期崩溃 | `memory` |
| **②** | **UI 卡顿** | 主线程同步 IO 与重计算、`setState` 时机不当（build 期间触发 rebuild）、**依赖未建立就用**（`initState` 里 `Theme.of`）、build 内建对象、rebuild 范围过大、长列表全量构建、saveLayer 等渲染开销 | `jank` |
| **③** | **网络与并发** | 扇出无上限、轮询叠加、无防抖/无守卫、**拦截器耗时操作**、**新请求前是否取消旧请求**、**大 JSON 解析在哪个 isolate**、**请求失败异常是否被接住**、异步竞态、Future 被丢弃 | `net` |
| **④** | **代码结构** | 逐字重复与**结构重复（复制后改名）**、死代码、超长文件与方法、UI 直接依赖具体实现、上帝类、全局可变单例、包导出面失控、枚举 switch 兜底 | `structure` |
| **⑤** | **全量** | 以上全部，外加开发规范与 lint | `all` |

原来单列的「常见问题」已并入 ①②③——它是按「能不能在调试期发现」分的，和其他几个按主题分的不是同类项，内容本来就散落在三处：**用得太晚**（对象已销毁）归 ①、**用得太早 / 错误的帧阶段**归 ②、**竞态 / Future 丢弃**归 ③。合并后五个方向互不重叠，用户不会再为「我这算常见问题还是内存问题」犹豫。

**必须问，没有默认值。** 不要自己替用户选，也不要"先按全量跑着"——方向决定了后面读什么、查什么、报告覆盖什么，选错了整份报告都偏。扫描脚本的 `--focus` 是**必填参数**，没问过就跑不起来。

**用 `AskUserQuestion` 把五个选项摆出来问**（允许多选），然后：

- **用户的话里已经透出方向时，把那一项排在第一位并标「推荐」**，理由写出来。比如用户说"页面来回进出内存一直涨"，就把 ① 放第一并注明"你提到内存持续增长，这一项最对症"。**仍然要问**——推断只是帮他省一次思考，不是替他决定。
- 常见对应关系：内存一直涨、闪退、报 `setState() called after dispose` → ①；列表滑动卡、点了没反应、切主题后界面不对 → ②；接口被打爆、请求太多、搜索结果错乱、拦截器 → ③；代码太乱、复制粘贴多、想重构、难加需求 → ④；上线老出说不清的问题、或说不清方向 → ⑤ 全量。
- **多选就把对应的 `--focus` 分别跑一遍**，或直接用 `all`（选了三项以上时 `all` 更划算）。**④ 代码结构和 ①②③ 完全不重叠**——查运行期故障时它一条都不会出现，想顺带整理代码必须单独勾上，否则用户会以为「报告里没提重复代码就是没有」。
- 顺带把耗时差异告诉用户，他才好选：定向大约是全量的一半时间。

**唯一的例外是确实没人可问**（定时任务、用户明确说了自己离开）。这种情况下走 `all`，并在报告的「分析方向」栏写明"**未指定方向，无人应答，默认全量**"——让读报告的人知道这个方向不是他选的。除此之外一律要等用户回答，不要自己往下走。

方向定了之后，第 1 步的扫描加上 `--focus`，第 2 步照它给的主题取清单——两边都会自动收窄。

**报告里必须写明分析方向和未覆盖的方向**，例如「本次仅查崩溃与内存；UI 卡顿、网络与并发、代码结构均未纳入」。**定向报告不能看起来像全量报告**——用户会以为没写的就是没问题。

### 第 0.5 步：清点体量

```bash
find <pkg>/lib -name '*.dart' | wc -l
find <pkg>/lib -name '*.dart' -exec wc -l {} + | tail -1
```

| `lib/` 体量 | 做法 | 实测耗时 |
|---|---|---|
| ≤ 2000 行 | 全量精读，不用问 | 3–5 分钟 |
| 2000–6000 行 | 全量精读，但**开工前说一句**预计耗时，说完就开始，不等回复 | 8–20 分钟 |
| > 6000 行 或 > 80 文件 | **停下来问**，给出全量 / Top 20 线索密集文件 / 指定目录 / 指定文件四个选项，**填真实数字**（写"可能有点多"没有任何用） |

耗时曲线是**先平后陡**：2000 行以内几乎不随体量变化（大头是固定成本）。

**超标且没人回答**：按线索密度 + 体量取 Top 20，优先 widget/state 文件，报告开头写清精读了哪些、其余只做扫描。**漏检不可怕，假装读完了才可怕。**

未精读的文件里，若扫描显示它和已读文件高度同构（同一套模板复制 N 份），可以用 `diff` 实际比对确认后写成"该问题在 X 个同构文件中同样存在（已用 diff 核对）"。**没比对过就不要推广。**

### 第 1 步：跑扫描脚本

```bash
python3 <skill目录>/scripts/scan_package.py <pkg路径> --focus <方向>
```

`--focus` 是**必填**，取值来自第 0.2 步用户的选择（`memory` / `jank` / `net` / `structure` / `all`）。不传会直接报错——这是防止跳过"问方向"那一步的机械保证。定向扫描只输出该方向的线索，并只推荐该方向需要的清单章节。

输出的是**线索**不是结论，但**每条都附了源码证据**：命中行原文、所在类的 `dispose()` 全文、dispose 里调用的私有方法原文、重复度统计。末尾会给出该读哪几节清单的命令。

**正则会误报**，但多数误报靠脚本给的证据就能当场排除（比如资源其实在 `_cleanUp()` 里释放了、controller 是外部传入的）。**证据不足以定案的才去 Read 原文**，复核不了的线索直接丢掉——宁可漏报不可误报。

### 第 2 步：按扫描指引取清单

照抄扫描输出末尾那行命令，**一次调用取回全部所需章节**：

```bash
python3 <skill目录>/scripts/ref.py core memory timer net ...
```

`core`（高频误报清单）永远要取。写报告前再单独取 `template`。**不要 Read 整份 `checklist.md` / `common-pitfalls.md`。**

### 第 3 步：跑 analyzer（能跑就跑）

```bash
cd <pkg> && flutter analyze --no-fatal-infos 2>&1 | tail -60   # 或 dart analyze
```

跑不起来（没装 SDK、没 pub get）不要卡住，降级为纯静态阅读，报告开头写明「lint 部分未经工具验证」。

降级后 P3 只写**肉眼可确认的事实**：未使用的 import、`print`、空 catch、命名、缺 dartdoc。**不要断言编译器行为**——某个 `!` 能否靠类型提升省掉、某个构造能否加 `const`、某段代码是否真不可达，取决于字段是否 public/final 等细节，没跑工具就是猜。

**顺手看一眼 `analysis_options.yaml`**：`cancel_subscriptions`、`close_sinks`、`discarded_futures`、`unawaited_futures`、`avoid_void_async` 是官方 lint 规则但 `flutter_lints` **默认不启用**，恰好覆盖资源泄漏和异步失控。没开就是一条该写的改进建议，并要关联到它本可拦住的具体问题。

### 第 4 步：精读与取证

读的顺序按危害排：`State` 类（泄漏主战场）→ `build()` 方法体（卡顿主战场）→ 网络调用点（并发主战场）→ 包结构与依赖方向 → 重复与封装。

**每一个 Timer 单独走四问**（清单 `timer` 主题有展开）：能不能停 / 会不会没停旧的又开新的（**要全文搜创建它的方法被调用几处**）/ 回调会不会引发大量并发 setState / 会不会引发大量并发请求。第 2 问和第 4 问同时命中时要关联起来写。

**每个并发扇出点要追集合来源**：`Future.wait(ids.map(fetch))` 的并发数等于集合长度。写死的常量小集合不是问题，来自接口/数据库/用户选择就是隐患。追不到就写"取决于运行时数据量，建议确认上界"。

**网络层还要单独查这四件事**（清单 `net` 主题的 6.4–6.7 有展开）：

1. **拦截器里有没有耗时操作**——拦截器是全局放大器，开销乘以请求总数且跑在 UI isolate 上。把 `onRequest`/`onResponse`/`onError` 三个方法体完整读一遍，逐行问"这行乘以一万次请求还能接受吗"。最高频的一条是日志拦截器打印完整响应体（每个响应一次完整 `jsonEncode`）。顺带查 `handler.next/resolve/reject` 是不是每条分支都恰好调用一次——漏掉的那条会让请求**永久挂起**，表现为"点了没反应"，不报错也不超时。
2. **新请求发起前有没有取消旧的**——反复触发的入口（搜索、下拉刷新、切 tab、切筛选）如果不取消上一个，连接和流量双份浪费，旧响应还可能后到覆盖新数据。Dio 用 `CancelToken` 且**创建新 token 前必须先 cancel 旧的**；`package:http` 取消不了，只能用序号丢弃结果（这只解决覆盖，不省流量，高频入口仍需 debounce）。还要确认有 `CancelToken.isCancel(e)` 过滤，否则主动取消会被当成网络错误弹给用户。
3. **大 JSON 在哪个 isolate 解析**——`jsonDecode` 加上紧随其后的 `.map(fromJson)` 是两段主线程开销。修法是 Dio 配 `BackgroundTransformer`，或 `ResponseType.plain` + `compute` 一次做完。**影响取决于返回条数，先确认接口分页上限**，查不到就如实标注，别断言卡顿；小响应硬上 `compute` 反而更慢。
4. **请求失败的异常有没有被接住**——重点查用 `package:http` 却不判 `statusCode` 的地方：**http 对 4xx/5xx 不抛异常**，会照常返回，直接 `jsonDecode(resp.body)` 就是去解析一个 HTML 错误页，报出来的 `FormatException` 完全误导人。另外看错误有没有分类（超时/无网络/401/500 对用户是不同的事）、有没有统一出口。

**重复代码要专门走一遍**：结构重复（复制后改名）比逐字重复更值得看，grep 搜不到、肉眼扫不出。拿到重复组后打开两三处实际比对——**已分叉（一处加了判空/重试，另一处没有）是 P1 正确性问题，不是 P2 整洁问题**。同一个根因被复制 N 份要合并成一条并列出全部位置，改造方案给能根治的封装。

**收证据时问自己三件事**：能贴出触发问题的确切代码吗（不能→不写）？能说清是 Flutter 的哪个机制导致的吗（不能→降级或不写）？方案用的 API 在这个包的 SDK 约束和现有依赖下确实存在吗（不确定→换写法）？

**判断什么不该写**：调试期跑一遍就能发现的问题（红屏、溢出警戒条、文本截断、缺 SafeArea、颜色硬编码、`GlobalKey` 重复）不进正文，最多 P3 列一行——开发者自己会解决，写进去只会稀释真正重要的结论。**例外**：若这类问题**大量**存在，说明项目可能根本没被完整运行过，那是比单个问题严重得多的结论，单独写一句。

### 第 5 步：定优先级

判据只有一个：**线上出事概率 × 严重程度**。不是"改起来容易不容易"。

| 级别 | 含义 | 典型 |
|---|---|---|
| **P0** | 必然造成资源泄漏、崩溃或明显卡死 | Controller/Timer/订阅未释放；主线程同步批量 IO 或大计算；State 被全局单例长期持有；扇出规模由外部数据决定且无上限 |
| **P1** | 明确的性能或架构风险，特定场景暴露 | 长列表全量构建；`setState` 引发整页 rebuild；UI 直接 new 具体网络/存储实现；搜索无防抖、分页无守卫、重试无退避；**已分叉的重复代码** |
| **P2** | 可维护性问题，不影响运行 | 一般性重复、冗余状态、上帝类、超长方法、硬编码 |
| **P3** | lint / 规范 | **只给位置，不展开** |

同级内按影响面排序。同一个 P0 被复制 N 份仍是 P0，只是合并成一条来写。

### 第 6 步：写报告前自检

报告发出去就是别人排期改造的依据，错一条的代价远大于慢五分钟。每条问题过一遍：

| 校验项 | 不通过怎么办 |
|---|---|
| 报告里的「分析目录」和第 0 步确认的是同一个吗？还有别的 package 没纳入吗？ | 补上真实路径与未纳入清单 |
| 文件路径行号**重新核对过**吗？（读代码到写报告隔了很多步，行号最容易记串） | 重新确认，或去掉行号只留文件名 |
| 贴的代码片段和原文**逐字一致**吗？没有凭记忆改写？ | 重新复制原文 |
| 这条是**读到的**还是从线索**推测的**？ | 推测的回去读原文，读不了就删 |
| 方案里的 API/参数在该包 SDK 约束和依赖下**确实存在**？ | 换确定的写法，或标注「需新增依赖 xxx」 |
| 踩了 `core` 里的高频误报清单吗？（外部传入的 controller、间接释放、小数据量 `children:`） | 命中就删 |
| 每组重复**实际比对过**至少两处吗？ | 没比对不能定级 |
| 并发问题**查过集合来源**、说清上界了吗？ | 追来源；追不到写"取决于运行时大小" |
| 每个 Timer 的四问都答过吗？尤其「创建它的方法被调用几处」**搜过没有**？ | 去全文搜；只在 initState 创建的不报重复启动 |
| 命名像 `fetchXxx` 的调用**确认过真发网络请求**吗？ | 打开看，不是就删 |
| 优先级按"出事概率 × 严重程度"定的，不是按"改起来难不难"？ | 重新定级 |
| P3 条数压过 P0/P1 了吗？ | 说明没在真正读代码，回去补 |

### 第 7 步：写报告

按 `python3 scripts/ref.py template` 的结构写到 `package分析报告.md`（package 根目录，除非用户指定别处）。

**报告有两类读者：人和 AI 工具。** 后者要能检索定位、自动应用修复，所以格式是硬约束不是风格建议：

- 每条问题的字段名和顺序固定：**定位 / 锚点 / 现状 / 机制 / 改法 / 风险 / 难度 / 验证**，一个不少、不改名、不调换。
- **定位** 严格写 `路径:起-止`（相对 package 根，不带说明文字）。
- **锚点** 是从源文件**复制**出来的一行原文，在该文件中唯一——AI 工具靠它定位改哪一处。**直接取扫描输出里打给你的那行原文，或 Read 结果里的那一行，不要重新敲一遍，也不要为了验唯一性去逐条 grep**——第 8 步的校验脚本会一次性把存在性、唯一性、行号、逐字性全查掉，逐条 grep 是重复劳动。**编不出锚点，说明这条你没真正读过代码，删掉它。**
- **现状** 逐字来自源文件，只允许 `// ...` 省略中间行。**不许凭记忆改写**——直接从 Read 或扫描输出里复制。
- **改法** 标了「可机械修复=是」就必须是能直接替换现状代码块的完整片段；结构性改造标「否」并给分步骤，不要假装能一键替换。
- **验证** 一句可 grep 的代码事实或可观察的行为变化，供 AI 修复后自检。

**篇幅纪律**——报告是给人排期改造用的，不是越长越好：

| 级别 | 写法 | 篇幅 |
|---|---|---|
| P0 / P1 | 每条按上面八个字段完整展开 | 每条 25–40 行 |
| P2 | **合并同类项**：一张位置表 + 一个统一改造方向，不要每条开小节 | 整节 ≤ 60 行 |
| P3 | 一张表，一行一条 | 整节 ≤ 20 行 |

目标：**正文条目 ≤ 15 条，全文 ≤ 350 行**。超了就说明 P2 没合并、或代码片段贴太多、或在写教科书。超长报告的结果是没人看完，真正要紧的 P0 反而被淹没。

其余要点：开头是一屏读完的索引表；代码片段 ≤15 行只贴相关那几行；「机制」1–3 句讲清 Flutter 的哪个机制；P3 不给方案不给解释；全文中文但技术术语（dispose、build、rebuild）保留英文原词。**引用依据要准确**——清单给了确切的 lint 规则名和框架断言原文就直接引用，没有官方依据的标注"工程共识，无官方规则"；**别把规则讲反**（`avoid_slow_async_io` 恰恰推荐 `existsSync`/`statSync` 用同步版本，真正阻塞 UI 的是 `readAsStringSync` 这类批量读写）。

**某个维度认真查过没发现问题，要明确写出来**（"内存：逐一核对 12 个 State 的资源释放，未发现未 dispose 的资源"）。留空会让读者以为你漏检了。

### 第 8 步：跑校验（不通过不能交）

```bash
python3 <skill目录>/scripts/verify_report.py <pkg>/package分析报告.md <pkg>
```

它一次性逐条检查：文件存在吗、行号越界吗、**锚点在源码里真的找得到吗、是否唯一**、**「现状」代码块是否逐字来自源文件**。所以写报告时不必自己去验这些——写完跑一次即可，这比逐条 grep 快得多。

**这一步是"不瞎编"的机械保证**——编造的行号、虚构的锚点、凭记忆改写的代码，都会在这里变成 ❌。出现 ❌ 就回去核对源码改正那一条（改不出来就删掉它），**不要把没通过校验的报告交出去**。⚠ 提醒不阻断交付，但锚点不唯一会让 AI 工具改错地方，最好一并修掉。

校验通过后，在交付说明里带一句「已通过 verify_report.py 校验」——这是给用户的可信度凭证。

首次出报告时，每条问题的 **状态** 一律写 `待修复`，头部「修复进度」写 `0 / N`。

### 第 9 步：修复之后，回来标记（用户说改完了才做）

用户说"我修好了"、"帮我改一下这几条"、或有 AI 工具照着报告改完之后，**要回到报告里把状态更新掉**——报告是持续用的改造清单，不是一次性快照。没标记的话，下次谁也不知道哪些改过了。

```bash
python3 <skill目录>/scripts/verify_report.py <pkg>/package分析报告.md <pkg> --recheck
```

复查模式对照**当前**源码，把每条分成两类：

| 结果 | 含义 | 怎么处理 |
|---|---|---|
| **锚点仍在源码中** | 那几行代码没动过 → 问题仍在 | 保持 `待修复`。**若它已被标成「已修复」，脚本会告警——那说明修复没有落地**，要查清楚 |
| **锚点已不在源码中** | 那段代码改动过了 | 对照该条的「验证」字段确认改对了，再把状态改成 `✅ 已修复 YYYY-MM-DD（依据）` |

**锚点消失只能证明那几行变了，不能证明改对了。** 每条都要看「验证」字段——那个字段当初就是为这一刻写的。验证不通过就不能标已修复，如实写清楚现状。

标记时三处一起改：**每条的 `**状态**` 字段**、**索引表的「状态」列**、**头部的「修复进度 N / M」**。已修复的条目**不要删**——留着才有改造记录，回归时也好对照。评估后决定不改的标 `⏭ 不修（原因）`，原因必须写。

## 别踩的坑

**为凑数写问题。** 一个好 package 的报告只有 3 条问题是正确结果，不是失败。硬凑 P0 会让整份报告失信。

**把 lint 当正餐。** P3 有 40 条而 P0/P1 只有 2 条，说明没在真正读代码。

**给 Flutter 里不成立的建议。** 常见编造：说 `const` 能解决内存泄漏；说所有 `_buildXxx()` 都必须拆成 Widget 类（拆的收益在 rebuild 边界和 const 复用，要结合具体 rebuild 频率讲）；把 `setState` 说成"必须换状态管理框架"。

**推荐引入新依赖。** 优先用 SDK 自带能力和已有依赖。确需新包时明确标注「需新增依赖 xxx」并说明为什么自带能力做不到。

## 文件

- `scripts/scan_package.py` — 线索扫描，带源码证据，末尾给出该读哪几节清单
- `scripts/ref.py` — **按主题取参考章节，别整份读**；`--list` 看主题
- `scripts/verify_report.py` — **校验报告里的定位/锚点/现状代码是否真的对得上源码**，交付前必跑
- `references/checklist.md` — 六维度清单 + Timer 专项 + 高频误报清单（经 `ref.py` 取用）
- `references/common-pitfalls.md` — 只收「调试期发现不了 + 让 app 跑不正常」的时序故障（经 `ref.py` 取用）
- `references/report-template.md` — 报告模板（`ref.py template`）
