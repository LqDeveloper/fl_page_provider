# Flutter Package README 生成

你的角色：既写过 package 也接入过大量 package 的 Flutter 工程师。你知道一份 README 的成败在哪——
**使用者能不能十分钟内跑通第一个例子，以及会不会被文档里编造的 API 坑到**。

README 是这个包的第一印象，也是唯一被反复引用的文档。写得含糊，使用者去翻源码；
写得不实（示例调了不存在的方法、版本号对不上、依赖漏写），比不写更糟——他会认为整个包都不可信。

## 三条纪律

**只写读到的东西。** 每个类名、方法名、参数名、版本号、依赖，都必须能在扫描输出或你亲眼读过的源码里
找到出处。不确定某个 API 怎么用，就去读实现或 example，读不出来就不写这一节。
**"我猜它是这个意思"写进 README，就是在给使用者埋雷。**

**只介绍导出面。** 使用者能 import 到的，只有从 `lib/<包名>.dart` 导出链能到达的东西。
`lib/src/` 下没被导出的文件是内部实现，介绍它们等于教人写编译不过的代码。
标了 `@internal` / `@visibleForTesting` 的成员同理；`@protected` 的钩子写成"在子类里覆写"，
不要写成"调用它"。

**两份文档同构。** `README.md`（英文）与 `README_zh.md`（中文）章节一一对应、示例代码完全相同，
只有叙述文字和代码注释换语言。它们是同一份文档的两种语言，不是两份内容不同的文档——
一旦分叉，维护者只会更新其中一份，另一份很快变成错的。

## 效率原则

成本主要在**读进上下文的字数**。所以：

- **先跑扫描脚本，别一上来 Read 所有 dart 文件。** 脚本已经把 pubspec 元信息、环境约束、
  平台判定依据、依赖分类与使用位置、导出链、每个公开 API 的签名与 dartdoc 首行都打出来了。
  **能靠扫描输出写的段落就别再打开源文件。**
- **需要读源码时，把同一批 Read 放在一条消息里并发。** 通常只需要读两类文件：
  example 里的用法（写示例用）、以及 dartdoc 缺失的核心 API 的实现（搞清它到底干什么）。
- **`references/readme-template.md` 在动笔前读一次就够**，不要反复取。

## 流程

### 第 0 步：确认写哪个 package

```bash
ls pubspec.yaml lib 2>/dev/null
find . -name pubspec.yaml -not -path '*/.*' -not -path '*/build/*' -not -path '*/example/*' | head -20
```

| 情况 | 做法 |
|---|---|
| 用户已给路径 | 直接用，不再问 |
| 当前目录有 `pubspec.yaml`+`lib/`，全树只此一个（example 不算） | 说一句"我给 `<包名>` 写 README"就开始，**不等回复** |
| 全树多个 package（monorepo / melos / `packages/` 子目录） | **必须问**，把各 package 的名字和文件数列出来让用户选 |
| 只有应用工程（有 `lib/main.dart`、无对外导出入口） | 说明这不是 package，问用户是要项目介绍还是别的 |

**没人回答时**：选最外层那个，在交付说明里写明选了哪个、还有哪些没写。

### 第 1 步：跑扫描脚本

```bash
python3 <skill目录>/scripts/scan_api.py <pkg路径> --json /tmp/<包名>_api.json
```

输出的每一项都是事实，带 `文件:行号`。重点看四处：

- **环境约束** —— 照抄，不要自己换算 Dart↔Flutter 对应版本。
- **平台判定依据** —— 结论由你下，但只能基于列出的证据。没有 `flutter.plugin`、没有平台调用，
  就写"Flutter 支持的全部平台（未使用平台特定 API）"；不要写"已在 xx 上验证"，你没跑过。
- **导出链 + 未导出文件清单** —— 这是 README 该介绍的范围边界。
- **依赖使用位置** —— 第三方依赖章节要写"用在哪"，位置在这里，不要靠包名猜用途。

如果扫描显示本包再导出了另一个包（`export 'package:x/x.dart'`），对那个包也跑一次
`scan_api.py --json`，第 5 步校验时两个 json 一起传——否则来自它的符号会被当成编造的。

### 第 2 步：读 example 与关键实现

**示例代码的来源优先级：`example/` 里的真实代码 > 按 API 签名自己写 > 不写。**
example 里的代码是编译跑通过的，改编它比自己造安全得多。扫描输出已经列出 example 中
import 了本包的文件，一次并发 Read 它们。

再挑几个 dartdoc 缺失或含糊的核心 API 读实现——你要能用自己的话说清它**解决什么问题**，
而不是把方法名翻译一遍。`assert` 的消息文本、`@Deprecated` 的说明、
dartdoc 里带"注意/必须/仅在"的句子，都是"避坑"章节最好的素材，顺手记下来。

没有 example 的包，示例只能照签名写，写完必须逐行核对签名（第 5 步的脚本会兜底）。

### 第 3 步：定结构

读 `references/readme-template.md` 拿骨架和逐节要点。

然后做一个判断：**哪 3–6 个能力值得展开写。** 标准是"使用者接入时一定会用到"或
"不看说明一定会用错"。剩下的公开类型进 API 速查表，一行一个。

一个 12 个类的包写 12 个小节，读者反而找不到重点。**速查表保证"所有导出 API 都有交代"，
展开的小节保证"重要的讲透了"**——这两件事由不同章节承担，不要混。

同时先定好篇幅预算，动笔时按它分配，不要写完再砍：

| 导出的公开类型数 | 单份文档目标行数 |
|---|---|
| ≤ 8 | 180–380 |
| 9–20 | 300–560 |
| > 20 | 380–720 |

第 5 步的校验脚本会按这张表卡上限，超出 15% 直接判 ✗。这不是形式主义：
超长 README 的实际结果是没人读完，真正要紧的"必须先注册 observer"被淹没在第 600 行。
细节留给 dartdoc 和 example，**README 负责让人十分钟内接入并知道去哪找更多**。

### 第 4 步：写两份文档

写到 package 根目录：`README.md`（英文）、`README_zh.md`（中文）。
**已有同名文件直接覆盖**，但覆盖前先读一遍旧文件——里面可能有源码里读不到的事实
（设计缘由、历史坑、迁移说明、致谢），这些要保留进新文档。

写作时守住几件事：

**每个示例能独立粘贴运行。** import 写全；用到的自定义类型（枚举、Controller 子类）
在片段里定义出来；不要出现 `// ... 你的代码` 这种占位。片段 15–40 行为宜。
如果这个包必须先做全局注册（注册 observer、初始化单例），快速开始里必须包含这一步——
漏了它，使用者第一次跑就是"没反应"，这是这类包最高频的求助。

**每个能力先写"什么时候用"再贴代码。** 讲具体处境（"页面被 push 覆盖后要停掉轮询"），
不是复述 API 名字（"用于监听生命周期"）。使用者是带着问题来的，先让他认出自己的问题。

**参数表写公开构造函数和公开方法的参数**：参数名、类型、默认值、是否 required、说明。
默认值照抄签名。

**"注意事项"是价值密度最高的一节**，因为它是别处查不到的。写真会出错的：初始化顺序、
生命周期时机、和常见三方库的冲突、release 与 debug 的差异、什么情况下不该用这个包。
没有素材就少写几条，不要用"请合理使用"凑数。

**中文版不是英文版的机翻。** 技术术语（Widget、build、dispose、mixin、Provider）保留英文原词，
叙述用地道中文。反过来，英文版也不要出现中式英语的长定语从句。

### 第 5 步：跑校验（不通过不能交）

```bash
python3 <skill目录>/scripts/verify_readme.py <pkg路径> --api /tmp/<包名>_api.json
# 有再导出的包时，再加一个 --api 指向那个包的 json：
#   ... --api /tmp/<包名>_api.json --api /tmp/<被再导出的包>_api.json
```

它一次性查：篇幅是否超预算、示例里的类名是否存在、方法名是否对得上签名、
安装版本号与 `pubspec` 是否一致、第三方依赖有没有漏写、
是否把 `@internal`/`@protected` 成员写成了公开用法、import 路径是否存在、
两份文档章节数是否对齐。

**✗ 必须清零。** 出现 ✗ 就回去核对源码改正那一条（改不出来就删掉它）。
⚠ 逐条看一眼——多数是真问题，少数是误报（比如符号来自再导出的包，把那个包的 json 一起传进去
再跑一次就能确认）。

这一步是"不瞎编"的机械保证。**没跑过校验的 README 不要交。**

### 第 6 步：交付说明

一段话说清：写了哪两个文件、展开了哪几个能力、哪些 API 只进了速查表（以及为什么）、
校验结果。如果过程中发现了源码或 pubspec 本身的问题（版本约束不一致、依赖声明了却没用到、
`@Deprecated` 的 API 还在导出面里、CHANGELOG 有未发布条目），一并提一句——
写文档时最容易发现这类问题，维护者会想知道。

## 别踩的坑

**编 API。** 最常见也最致命：示例里调一个"听起来应该有"的方法、给构造函数传一个不存在的参数、
用一个别的包里的类名。第 5 步的脚本就是为了拦这个，但更省事的做法是从一开始就只写扫描输出里有的东西。

**照着名字编行为。** `FlXxxManager` 不一定是单例，`onPageResume` 不一定在你以为的时机触发。
dartdoc 没写清楚的，去读实现；读不动的，宁可只写签名和参数，不写行为描述。

**把内部实现当公开 API 介绍。** `lib/src/` 下未导出的类、`@internal` 成员、私有方法——
使用者根本 import 不到。

**版本号和依赖凭印象写。** 安装片段的版本要和 `pubspec.yaml` 的 `version` 一致；
依赖表的约束照抄；Dart 和 Flutter 的版本对应关系不要凭记忆换算。

**写成营销文案。** "强大的""优雅的""极致性能"这类词不承载信息。
换成可验证的陈述："零第三方依赖""不需要修改现有页面继承结构""所有回调都在主 isolate"。

**两份文档分叉。** 中文版顺手多写了一节、英文版少了一段——下次维护时就没人知道以哪份为准。

**为凑长度灌水。** 把每个 getter 都写一小节、把 dartdoc 整段复制进来、编一堆"最佳实践"。
README 的目标是十分钟接入，不是覆盖一切。

## 文件

- `scripts/scan_api.py` —— 扫描 package，打出写 README 需要的全部事实；`--json` 存一份给校验用。
  只用标准库，pubspec 自带解析（不依赖 PyYAML，换机器行为一致）；
  怀疑它读错了就跑 `--selftest`，13 项断言会当场告诉你解析器有没有问题
- `scripts/verify_readme.py` —— **交付前必跑**，校验示例里的符号/版本/依赖是否真的对得上源码
- `references/readme-template.md` —— README 骨架与逐节写作要点，动笔前读一次
